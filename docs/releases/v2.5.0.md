A new flag, `-s/--streams`: how many HTTP/2 streams one connection keeps in
flight. zrk shipped HTTP/2 in v2.4.0 with exactly one request per connection and
stopped there deliberately; this is the other half, and the reason it took a
release of its own is that the interesting part was never the plumbing.

## `-c` still means what it meant

The obvious way to spell multiplexed concurrency is h2load's: `-c` connections
times `-m` streams, so `-c 10 -m 10` and `-c 100` are both "100 requests in
flight" and you pick whichever you like. zrk does not do that, and the flag is
deliberately not a second concurrency dial.

`-R` still splits evenly across `-c` connections. Each connection still owns one
send schedule and one request index, and every latency sample is still measured
from the time its request was *scheduled*. All `-s` does is bound how many of
that connection's already-scheduled sends may be on the wire at once. It never
changes what is due, or when.

So `-c` remains the number to compare across runs, exactly as in every earlier
release, and `-s 1` — the default — is the old behaviour down to which code path
runs.

## `-c 10 -s 10` is not `-c 100`

Against `nghttpd` on loopback, closed loop, five seconds each:

| layout | in flight | req/s | p50 | p99 |
| --- | ---: | ---: | ---: | ---: |
| `-c 10 -s 1` | 10 | 250,990 | 38 µs | 67 µs |
| `-c 10 -s 10` | 100 | 524,942 | 165 µs | 235 µs |
| `-c 100 -s 1` | 100 | 186,608 | 522 µs | 1.04 ms |
| `-c 100 -s 10` | 1000 | 433,818 | 2.21 ms | 3.77 ms |

The two middle rows are the same hundred concurrent requests and nothing else:
**2.8× apart on throughput, 3.2× apart on p50**. h2load, asked the same two
questions on the same server, splits the same way — 857k req/s at `-c 10 -m 10`
against 285k at `-c 100 -m 1` — so this is a property of the load layout, not of
either tool.

Which way the gap points is worth noticing. On loopback, multiplexing *wins*: a
hundred sockets cost a hundred sockets' worth of syscalls and scheduling, and
ten do not. That is the argument for `-s` existing. It is also the argument for
never quoting a `-s` number against a `-c` number, because the difference is
whatever the client's own transport costs on that machine — the exact quantity a
load generator exists to keep out of its results.

Change `-c` when you want a number to compare. Change `-s` when you want to
model a client that multiplexes, or to let a connection hold its schedule
instead of waiting out each response. [docs/multiplexing.md](../multiplexing.md)
has the full reasoning.

## Aborting one stream, not the connection

With one request in flight, a timeout is aborted by shutting the socket down,
because "abort this request" and "abort this connection" are the same act. With
several streams open they stop being the same act, so a blown bound is now spent
on a `RST_STREAM` for the stream that blew it, and every other in-flight
response goes on arriving. `--deadline-abort` inherits this and improves on it:
serially it costs a connection reset per miss, which is why
[deadlines.md](../deadlines.md) warns against it under saturation; per stream it
is a reset of the stream alone, with no reconnect storm.

h2load has no precedent to copy here — it has no per-stream timeout at all, only
per-connection `-N`/`-T`, and its connection timeout marks *every* in-flight
stream timed out and disconnects.

## Nagle is off now, on every connection

zrk sets `TCP_NODELAY` on every socket it opens, HTTP/1.1 included. This is a
behaviour change for existing runs, and it is the one thing in this release that
can move a number you already had.

Nagle's algorithm holds a small write until the previous one is acknowledged,
and Linux delays that acknowledgement by up to 40 ms. Serially the two barely
meet: nothing of ours is unacknowledged when the next request is written,
because the response that acknowledged it is what released the send. That is why
this was never noticed. Multiplexing makes them meet by design — writing a
second request while the first is outstanding is the whole point — and Nagle
answers by parking that request until a delayed-ACK timer fires, putting 40 ms
of the client's own transport into the target's latency.

Most HTTP/1.1 runs will not move at all, for the reason above. Runs that do
should move *down*, and were being told 40 ms about the client that they were
attributing to the server.

## Also

- **`SETTINGS_MAX_CONCURRENT_STREAMS` is honoured.** The effective depth is
  `min(-s, peer limit)`, read from the handshake, so it is known before the
  first send rather than discovered by overshooting. h2load ignores it, and the
  surplus does not fail — it queues, invisibly, inside the client.
- **The connection receive window is replenished.** It was opened once to its
  31-bit maximum and never revisited, which reads as "flow control off" and is
  not: that window is a budget for the connection's whole life, and every DATA
  octet spends it. Now credited back at half — one `WINDOW_UPDATE` per gibibyte.
- **Responses ending in trailers complete.** A trailer section carries no
  `:status`, and decoding one as though it must have failed the request. gRPC
  ends every response this way. Previously an error, now a normal completion,
  on the HTTP/1.1-shaped serial path as well as the multiplexed one.
- **`--format json` gains `config.streams`**, so a harness collecting several
  layouts can tell them apart in the result files.

## Upgrading

Nothing changes unless you pass `-s`, with the one exception above: `TCP_NODELAY`
now applies to every connection, and if that moves a number it moves it toward
the server's real latency. `-s` requires `--http2`, rejects a depth above 128,
and defaults to 1.

If you benchmark a target that sends trailers, its responses were being counted
as read errors and are now counted as successes — expect the error rate to drop
and the completion count to rise.

`zig build test` covers 297 tests, 12 new: the CLI surface, that two streams are
genuinely open at once (proven structurally, against a server that will not
answer request *k* until *k+1* arrives, so a serial client deadlocks), that a
stalled stream is reset alone while its neighbours' samples survive, that depth
leaves the offered load alone, that a trailer section completes, and that a
connection dying with eight streams open charges each request exactly once.
